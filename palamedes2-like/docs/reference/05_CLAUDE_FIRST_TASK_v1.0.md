# Claude Code 初回開発指示書 v1.0

作成日：2026-10-18  
対象：パラメデス２風ゲーム制作／新規開発の初回指示

この指示書と、ユーザーがClaudeへ貼り付けた開始命令を受けて作業を開始する。ChatGPTが指示書を保存した時点で開始したことにはしない。

## 1. 役割と今回の到達目標

あなたはプログラマー。ChatGPT Workは企画・仕様管理・レビューを担当する。Claudeへのプログラミング依頼は今回が初回であり、既存実装がある前提を置かない。

最終目標は、640×360・16:9・16bit風のブラウザパズルゲームで、CPU対戦と1台PCでのローカル2人対戦を完成させること。オンライン対戦、本番画像制作、ひたすら/QUEST等の発展モードは今回対象外。

今回の到達目標は、適切な開発環境を設定し、確定済みのゲームロジックと表示・アニメーションを実装した、ブラウザで操作できる基本動作検証版を納品すること。未確定の攻撃力・消去・勝敗ルールを埋めて、対戦完成版と称してはならない。

計画の提示だけで止めず、環境確認→設定→実装→自動テスト→ブラウザ確認→修正→共有先への納品まで、可能な作業を連続実行する。

## 3. 最初に行う作業環境の設定

### 3.1 実行能力を確認する

現在のOS、シェル、実際の作業ディレクトリ、書込み可能範囲、ターミナル/ファイル操作/ブラウザ検証の利用可否を確認する。Windows上での開発・利用を基本とするが、実行環境がLinuxやクラウドなら実態を記録し、Windowsで再現できる成果物を用意する。Windows環境やローカルPCへ接続できていると推測しない。

共有Driveの一覧・全文取得・PNG取得・新規ファイル保存が可能かを、利用できる接続手段で確認する。ChatGPT側の接続や資格情報がClaudeにも引き継がれるとは考えない。既存の認証済み接続または実在する同期フォルダを使用する。URLが開けることと、ファイルの取得/保存ができることを区別する。

ターミナルも実ファイル書込みもない通常チャット環境なら、コード本文を大量出力して開発した扱いにしない。Claude Codeが動く作業環境への切替という不足事項を具体的に報告する。認証/権限が不足する場合も、使える手段を確認したうえで必要な設定だけをまとめて依頼する。共有設定の公開化、権限拡大、APIキーの新規発行を勝手に行わない。

### 3.2 作業用プロジェクトを分離する

利用可能な既存作業領域を確認し、その配下に専用の `palamedes2-like` プロジェクトを作る。パスは実態から決定して記録し、他セッションのパスを自分の環境にあると仮定しない。すでに同名プロジェクトが存在する場合は、内容・Git状態を調べてから利用する。既存データを初期化しない。

共有Driveは正式仕様・素材原本・納品物の共通保存先とし、開発中の依存関係やキャッシュを共有先へ直接大量生成しない。同期Driveが使える場合も、通常の作業コピーでビルドし、必要な成果だけを納品する。

推奨構成（名称の軽微な変更は可）：

```text
palamedes2-like/
  docs/reference/       取得した仕様の読取り用コピー
  docs/                環境記録・技術選定・引継ぎ
  public/assets/       仮PNG7枚
  src/core/            表示に依存しないロジック
  src/input/           1P/2P・将来CPUの入力窓口
  src/view/            描画・補間・スプライト再生
  tests/               自動テスト
  package.json
  lockfile
  README.md
```

原仕様・納品PNGは読取り参照とし、変更しない。将来の画像差替えでゲームロジックを改造しない構造にする。

### 3.3 ランタイム・依存関係・バージョン管理

Git、Node.js、パッケージマネージャーの利用可否・実バージョン・空き容量を確認する。既存環境を優先し、不足時に限りプロジェクトで必要なものを追加する。既存グローバル環境の破壊的な入替えや、無関係なツールの導入はしない。

TypeScript＋Phaserは候補。採用する場合は互換性と公式資料を確認し、ビルドツール・テストツールも含め最小限の構成を選び、選定理由を短く記録する。他方式を選ぶ場合も要求に対する理由を残す。パッケージマネージャーは1種類に統一し、lockfileを保存。使用したNode/ツール版を記録してクリーン環境で再現できるようにする。

専用作業ディレクトリでGitを使用する。未初期化ならローカルリポジトリを作成可能。既存変更を消さず、`node_modules`、キャッシュ、機密情報を除外する。Git author設定は既存を使い、必要な値がなければ捏造しない。コミットできなくても作業ファイルと納品を保存し、その点を記録する。リモートGitHubリポジトリの作成・push・公開は今回行わない。

開発サーバー、ビルド、型検査、自動テストを実行する共通スクリプトを用意する。サーバーはローカル利用を基本とし、ホスト/ポートと停止方法をREADMEへ記載。実行版を単にHTMLのダブルクリックで起動できると仮定せず、必要なローカルHTTP起動方法を用意する。

### 3.4 環境確認の完了条件

`docs/ENVIRONMENT.md`へ、OS/シェル/実作業パス、Git/Node/使用ツールの版、依存導入方法、起動/テスト/ビルド方法、共有先への取得/保存方法と確認結果を記録する。トークン・Cookie・鍵は含めない。

最低限の起動とテスト実行ができ、仮PNGとJSONが読み込めることを確認後、そのまま実装へ進む。環境設定だけで最終報告を出して止まらない。初回の納品保存時には、共有先でファイル名・サイズ・保存フォルダを読み戻して確認する。

## 4. 今回の実装範囲

### 4.1 ロジック

- ピース24種、原則均等生成、乱数を差し替え可能な構造、MATCH下側3段18個初期配置。
- 盤面・列・ピースID、移動中ピース、予約空白、共通基準を分離管理。
- 発射時には列を詰めない。到達時に成功判定し、成功後に基準更新・役ストック追加・予約解除・上詰め。同一到達フレームは1P優先し、2Pは更新後の基準で判定。
- 失敗帰還、列ロックと他列/相手の継続、B循環。
- ストック6個、7個目の最古破棄、4/5/6個の部分集合判定、同じ部分集合の数字/属性役、最強属性1種、属性単独成立、複合翻数加算・二重加算禁止、宣言時全消費。
- 攻撃ストック0〜29飽和、最大3の波、容量不足保持、被攻撃者演出中WAITなど確定部分を独立モジュールとして実装・テスト。
- 自然/手動上昇32px、予約追従、宣言側の停止対象タイマーを実装。未確定の敗北分岐は分離する。

未確定の同点優先や同一プレイヤー複数発射を独断で決めない。該当経路を未解決として分離し、確定経路・独立モジュールの実装を進める。自動テスト用のイベント注入は許可するが、仮ルールを通常プレイに隠して組み込まない。

### 4.2 表示・入力

- 論理640×360、6列×7段・32pxセル。拡大時はドットを滲ませない。
- 仮PNG7枚を使用。マニフェストから切出し、必要フレームを再生。小型ピース開始Y96。予備透明枠を通常アニメーションへ混ぜない。
- キャラ左右TWEEN、キャラFRAME、距離に依存しない同一所要時間の直線発射、成功後上詰め。
- 高速山なり→元列X→低速垂直下降→最新予約位置へSNAP。下降開始/終了時刻は固定し、盤面上昇でも所要時間不変。
- B最上段ピースは暗色・通常ピース背面を通って最下段へ。キャラはslot12〜15の1枚を一瞬表示し、座標は不変。
- 攻撃アイコンは大2個まで、小は左5・右4。起点/間隔は画面JSONどおり。
- 描画順はキャラ/役名＜帰還＜打上げ。ストック50＜背面光55＜キャラ60＜前面光65は数値どおり。
- 役名16種各3フレーム、宣言者だけ操作ロック、相手継続。
- 1P/2P入力を別系統にする。キー割当は変更可能なテスト設定と明記。CPUは共通入力窓口へ後から接続可能にし、今回は未確定CPU戦略を正式仕様化しない。

アニメ時間/fps/曲線高さ/暗度はテスト用初期値を選定・集約してよい。攻撃算式、消去範囲、勝敗、連鎖の正式適用条件とは区別する。

## 5. 未確定事項と進行方法

台帳G01〜G06は未確定。翻→消去→攻撃、相殺端数/送信順、消去方向/確定時刻、敗北猶予、無役宣言、同点、発射/入力の境界、同時イベント全順序、倍率適用、先取本数等を勝手に正式確定しない。

未確定部分は依存する機能を保留し、確定済み部分とテストを継続する。重大な矛盾で有効な作業が進まない場合だけ、該当箇所・選択肢・影響・推奨案をまとめて質問する。既に資料で未確定と明記されている全項目を、初手で一問ずつ質問して停止しない。

## 6. 検証と初回納品の合格条件

1. 依存導入・起動・ビルド・テストの手順をREADMEから再現できる。
2. 表示非依存の成功判定、到達競合、ストック、部分集合、予約、29上限等を自動テストで確認。
3. 帰還中の上昇でも固定時間・最終座標一致・二重生成なし。他列と相手の操作が継続する。
4. ブラウザで全PNG読込、主要モーション、Bポーズ、役名色替え、座標/描画順を確認。実際に起動して操作し、コンソール/ネットワークエラーも調べる。
5. 攻撃表示0〜29を検証し、左5右4・最大3波・保持/WAITの確定経路を確認する。
6. 描画FPSや補間完了コールバック順がゲーム結果を変えないことを検証する。
7. 操作可能な基本動作検証版を納品。未確定で未実装の対戦機能をREADMEと報告で明示する。

ブラウザ自動化が使えない場合は、利用可能な検証手段を試したうえで未実施部分を記録し、ビルドPASSを目視PASSと称さない。人間にしかできない操作確認は実装後にまとめて依頼する。

## 7. 納品先と引継ぎ

| 納品内容 | 共有Driveの保存先 |
|---|---|
| ソースZIP、lockfile、テスト、README、環境記録 | 03_プログラム成果物/01_ソースコード |
| ビルド済み実行版ZIP、起動手順、操作説明 | 03_プログラム成果物/02_プレイ可能なテスト版 |
| テスト結果・検証範囲・既知問題・残課題 | 04_テスト・検証/01_テスト結果・不具合 |
| 必要な動作スクリーンショット | 04_テスト・検証/02_スクリーンショット・録画 |
| 短い進捗・次回開始点 | 00_共有ノート・進行管理 |

ソース/実行版/テスト報告は同じ版・日時で対応づける。ZIPへnode_modules、不要キャッシュ、資格情報を入れない。仮PNGと使用したJSONは再現に必要な範囲で同梱する。ブラウザ実行版を作るためにソースの再ビルドが必須という状態にせず、ビルド済み出力も添える。

最終納品前に、ZIPを別の作業ディレクトリへ展開して必要ファイルの不足がないか確認し、共有先へ保存後にファイルを再確認する。単なるチャット上のコード出力やローカル保存だけを共有納品完了としない。

既存の仕様書・原本画像は上書きしない。共通ノートに同時編集の競合がある場合は別の日時付き進捗ファイルを追加し、勝手に相手の変更を戻さない。

使用量やセッション制限が近い場合は、変更ファイルと再開メモを保存し、可能な成果を共有先へ納品する。未完成の範囲、実行したテスト、未実施、次の開始点を短く記録する。通常時の中間報告用UIや長文説明は作らず、実装・検証を優先する。
